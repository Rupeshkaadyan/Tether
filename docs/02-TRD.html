Architectural principle

Local-first. Every read is served from SQLite. The network is used only to sync. The app is fully usable on a plane, in a subway, or with a dead backend. This single decision eliminates an entire class of the sync bugs that affected the predecessor product.

Key client rules

  • No component talks to the network directly. Everything goes through the sync engine or a service layer. This keeps offline behaviour consistent by default.
  • Encryption happens at the service boundary, never in the UI. Components handle plaintext; the crypto service handles everything else.
  • Optimistic writes always. The UI updates instantly; sync confirms later. Users never wait on a spinner for their own action.
  • Feature flags from day one. Remote-configurable so you can kill the AI coach or a content track without a store release.

04Offline-first sync strategy

Write path

  1. User acts — writes a reply, taps a mood.
  2. Encrypt locally — content encrypted on device.
  3. Write to SQLite — committed to local store immediately.
  4. Enqueue in outbox — durable queue, survives app kill.
  5. Flush — when connectivity allows, batches of encrypted records.
  6. Ack and clear — server confirms, outbox entry removed.

Read path

  1. Pull with cursor — client sends last-synced cursor, receives only deltas.
  2. Decrypt and merge — into local SQLite.
  3. Emit to UI — observables refresh automatically.

Conflict resolution

Data typeStrategyRationale
Journal entriesLast-write-wins on updated_at, keep both versionsWrites are per-user and immutable in practice; collisions are near-impossible.
Mood logsLast-write-wins per user per dayNaturally keyed; no merge needed.
Profile / settingsLast-write-wins with monotonic versionLow-stakes, easily re-set.
Pairing stateServer authoritativeCorrectness matters more than latency. Never guess here.
StreaksServer computed, client displaysPrevents cheating and divergence.
Idempotency

Every outbox record carries a client-generated UUID. The server treats it as an idempotency key. This makes retries safe, which is what prevents duplicate entries under flaky mobile networks.

05Backend architecture

Supabase services used

  • Postgres — source of truth. Stores ciphertext for journal and chat; plaintext only for non-sensitive relational data.
  • Row Level Security — every table protected. A user can only ever read their own rows and their partner's shared rows.
  • Auth — Apple, Google, email OTP. No phone number, deliberately.
  • Realtime — pairing status, prompt unlock events, typing indicators. Used sparingly; most state arrives via pull.
  • Edge Functions (Deno) — AI proxy, safety classification, webhook handlers, scheduled jobs.
  • Storage — encrypted media only, private buckets.

Versioning

Edge functions are versioned in the path (/v1/) from day one. Client ships a minimum-supported-version header; older clients get a graceful upgrade prompt rather than a crash.

07Authentication and authorisation

  • Methods — Sign in with Apple (required by App Store if any social login is offered), Google, email OTP. No phone number — a competitor loses users at this step.
  • Sessions — JWT with refresh rotation. Biometric re-auth optional for the private vault.
  • Row Level Security — the real authorisation layer. Policies enforce: you see your rows; you see your partner's rows only where visibility = 'shared' and you are in an active couple.
  • Invite tokens — single-use or 7-day expiry, revocable, bound to the inviting user.
  • Anonymous pairing — a partner can redeem an invite before creating an account; state transfers on signup.

Requirements

  • Latency — first token under 3s at p95. Stream tokens, never block on full response.
  • Memory scope — retrieval is scoped to the asking user plus shared entries. Never retrieve the partner's private entries.
  • Caching — cache responses to common prompt patterns. Use a small fast model for classification, a large one for coaching.
  • Cost control — per-tier monthly message caps, token budget alerts, response length limits.
  • Refusal behaviour — must refuse gracefully and warmly, never lecture. A refusal that shames the user is a worse outcome than a slightly generic answer.

10Payments

  • RevenueCat wraps StoreKit 2 and Play Billing. Products: monthly, annual, Couples+ annual.
  • Shared entitlement — on purchase, write entitlement to both couple_members rows. Either partner purchasing unlocks both.
  • Webhook — handles renewal, refund, grace period, billing retry, and crossgrade.
  • Intro offers — 14-day free trial configured in App Store Connect and Play Console, surfaced through RevenueCat.
  • Restore purchases — prominent, one tap. Required by App Store review.
  • Cancellation — handled by the stores, but the app links directly. No dark patterns.

Scaling path

  • 0–10k users — Supabase free/pro tier. No changes needed.
  • 10k–100k — read replicas for pull, connection pooling (PgBouncer), edge function regionalisation, AI response caching.
  • 100k+ — partition prompt_replies and journal_entries by month, archive cold data, consider dedicated vector store if pgvector latency degrades.

15Environments, CI/CD, and testing

Environments

  • local — Supabase local via CLI, seeded fixtures.
  • staging — separate Supabase project, sandbox RevenueCat, test AI keys.
  • production — separate project, strict RLS, monitoring on.

CI pipeline

  1. Lint + typecheck — ESLint, strict TS. Fails fast.
  2. Unit tests — Vitest. Crypto, sync logic, streak math, Pulse computation.
  3. RLS policy tests — automated verification that users cannot read others' data. This is a release gate.
  4. Safety red-team suite — fixed corpus of crisis inputs; must classify correctly with zero misses.
  5. E2E tests — Detox or Maestro on the critical paths: onboarding, pairing, daily loop, paywall.
  6. Build — EAS Build, distribute to TestFlight / internal track.

Manual test matrix before release

  • Airplane mode: write 10 entries, reconnect, verify all sync and none duplicate.
  • Pairing: all three methods, including in-person QR with both devices offline.
  • Interrupted purchase, restore purchases, cancellation.
  • Dynamic Type at 200% on every screen.
  • VoiceOver traversal of the daily loop.
